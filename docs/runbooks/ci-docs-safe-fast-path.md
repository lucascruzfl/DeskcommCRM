# Fast path documental do CI

Em `pull_request.synchronize`, os quatro workflows chamam `scripts/ci-docs-safe-delta.mjs`. O script compara **somente** `before` com `pull_request.head.sha`, confirma que o HEAD da PR ainda é esse SHA, que `before` é ancestral e que cada check do HEAD anterior terminou `success`. Ele lê todas as páginas de check-runs (`filter=all`); quando há vários runs do mesmo context, todos precisam estar concluídos com sucesso. Erro, página truncada, check ausente, pendente, pulado, falho ou ID duplicado impõem CI completo. Rerun, abertura de PR, force push não ancestral, push na `main`, tag e dispatch não recebem o atalho.

O detector executado vem do SHA de base da PR, não do código que a própria PR propõe. Se essa base ainda não contém o detector (como na PR que introduz o mecanismo), o atalho responde `nao` e o CI completo roda.

Fonte de confiança do parent: proteção de `mcp/stable` medida pela API em 01/10/2026: `verify`, `invariants`, `e2e`, `imagens-ok`, todos do GitHub Actions (`app_id=15368`). `build-and-size` é exigido adicionalmente. O conjunto versionado `PARENT_TRUSTED_CHECKS` mora no script e é testado; ele não é uma consulta dinâmica da branch protection. O token padrão do workflow não pode consultar branch protection (a API requer `administration:read`), então alteração da proteção exige atualizar e revisar esse conjunto. A branch protection continua cobrando seus contexts no HEAD atual, sem bypass.

Allowlist inicial: `docs/**`, `tasks/**`, `evidence/**` para arquivos inertes (`md`, `txt`, imagens raster, `pdf`); `.changes/**` e `.github/ISSUE_TEMPLATE/**` somente `md`; `*.md` somente na raiz; `.github/*.md`. Esses caminhos não alimentam produto, banco, E2E, imagens nem o build do app: os detectores de alcance existentes também os classificam como inertes para seus domínios, e as pastas documentais ficam fora do contexto Docker. A busca de leituras de documentação identificou guardas de `verify` e o pipeline de release; por isso `verify` continua completo e `docs/mcp/RELEASE-AUDIT.json` fica fora. Qualquer guia de agente chamado `AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `GEMINI.md`, `SKILL.md` ou `copilot-instructions.md` é exceção e exige CI completo, mesmo numa pasta documental. Arquivo de código, configuração, workflow, script, migration, teste, symlink, modo executável, rename com qualquer ponta fora da lista, ou resultado ambíguo impõe CI completo.

No atalho, `verify-parte` continua rodando integralmente, com typecheck, lint, unit, cercas e auditorias; o agregado `verify` só aceita suas partes verdes. Isso é necessário porque `evidencia-citada`, `fragmentos-de-release` e `documentacao-aponta-para-o-que-existe` leem documentação, evidências e `.changes`. Somente PG15/PG17, as seis partes E2E, os builds de imagem em PR e o build pesado de `build-and-size` podem ser evitados. Os checks `invariants`, `e2e`, `imagens-ok` e `build-and-size` continuam presentes no HEAD atual e registram a prova no Job Summary. No caminho normal, as regras anteriores continuam. Uma cadeia de commits documentais só recebe atalho passo a passo: cada novo HEAD exige que o imediatamente anterior esteja integralmente verde.
